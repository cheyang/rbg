Why the rebase + field selector
--------------------------------
The original PR-434 branch predates the restartPolicy structuring that
shipped in the cluster's installed CRD/controller (v0.8.0-0c00546d, #418).
Running the raw PR binary cluster-wide failed every typed LIST with
  json: cannot unmarshal object into Go struct field ...restartPolicy
because the live RoleInstance/RoleInstanceSet objects store restartPolicy
as an OBJECT while the PR binary expected a string — a version-skew
artifact of the test setup, NOT a gang finding, but it globally blocked
reconciliation.

Rebasing onto upstream/main succeeded with ZERO conflicts (clean, so the
PR is cleanly mergeable). Upstream/main re-typed `restartPolicy` as a
string and moved the object to a new `restartPolicyConfig` key, so the
rebased binary decodes the live objects fine. To guarantee the live
workload is never touched, cacheOptions() was patched (test-only,
env-gated) to add a field selector metadata.namespace=v434-verify on the
RBG / RoleInstanceSet / RoleInstance informers. This yields a single
FILTERED SharedIndexInformer (no multiNamespaceInformer wrapper, so the
hard type assertions in stateful_instance_set_controller.go:103-104 still
hold — no panic) and excludes the nginx objects from the LIST entirely.

Result: controller cache synced with NO unmarshal errors and NO panic;
it reconciled only the v434-verify namespace.

Finding-by-finding live confirmation
-------------------------------------
BASELINE  minMember=2, both pods Running under schedulerName=volcano.
          The happy path works, so every red below is a product bug, not
          an environmental artifact.

F2  Role-name typo (`prefil` vs real `prefill`): PodGroup created with
    minMember=<none>/0. The typo silently DISABLES the gang constraint
    instead of being rejected. CONFIRMED.

F3  Excluded role still scheduled by volcano: minReplicas names only
    `prefill` (minMember=1), yet BOTH f3-excluded-prefill-0 AND
    f3-excluded-sidecar-0 carry spec.schedulerName=volcano and the
    annotation scheduling.k8s.io/group-name=f3-excluded — the excluded
    sidecar is bound into the same PodGroup whose minMember does not
    budget for it. CONFIRMED.

F4  minReplicas(5) > role replicas(2): PodGroup minMember=5 while only 2
    pods are ever created. The gang is unsatisfiable by construction;
    both pods stay Pending FOREVER (phase Inqueue). CONFIRMED — this is
    the most damaging: a single typo'd number wedges the whole group.

F5  minReplicas=0: accepted (no validation rejection), PodGroup
    minMember=<none>/0. CONFIRMED.

F6  `roles` scope ignored: policy scope is ["prefill"] ONLY, but
    minReplicas also names `decode`. PodGroup minMember=2 (=prefill 1 +
    decode 1) — decode joined the gang despite being out of the declared
    scope. The REQUIRED `roles` field is never read. CONFIRMED.

F7  Multiple gang rules: two rules (gang-prefill:1, gang-decode:1).
    PodGroup minMember=1 — only the FIRST rule survived; the second
    (decode) was silently dropped. Would be 2 if both counted. CONFIRMED.

F9  CoordinatedPolicy edits do not reconcile: patched baseline-ok policy
    prefill 2->3. PodGroup minMember STAYED 2 (policy now reads 3). Even
    after forcing an RBG reconcile (annotate poke) the PodGroup minMember
    remained 2 — the policy->PodGroup linkage is effectively one-shot and
    never re-derived. CONFIRMED (and stronger than predicted).
