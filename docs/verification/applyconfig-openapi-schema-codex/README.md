## Per-finding detail

### F1 — embedded schema does not match the API server's CRD schema

Mechanism. `hack/update-codegen.sh` feeds applyconfiguration-gen an OpenAPI document
generated by openapi-gen from the **Go types**. kube-apiserver instead builds the
field-management schema for custom resources from the **CRDs**. The RBG CRDs keep several
subtrees schemaless (`x-kubernetes-preserve-unknown-fields`): `Instance/RoleInstance
spec.components[].template`, `InstanceSet/RoleInstanceSet` instance templates,
`RoleBasedGroup(Set)` `templateRef.patch`/`templatePatch`/`leaderTemplatePatch`/
`workerTemplatePatch` and `customComponentsPattern.components[].template`. In those
subtrees the server tracks maps per key and each list as a whole (smd "deduced"), while
the embedded schema tracks the full Go/core-v1 structure (list-map containers keyed by
name, etc.). Additionally, the PR adds `+patchMergeKey=name`/`+patchStrategy=merge` markers
to v1alpha1 `InstanceSpec.Components`, whose CRD has no `x-kubernetes-list-type` — so the
server treats that list as **atomic** while the fake treats it as a **list-map**.

Observed at head (`results/parity-head.txt`):

- `TestFieldSetParityRoleInstance` / `…Instance` / `…RoleBasedGroup` /
  `…SchemalessSubtrees` (InstanceSet v1alpha1, RoleInstanceSet v1alpha2,
  RoleBasedGroupSet v1alpha2, RoleBasedGroup v1alpha1): **FAIL** — e.g. server records
  `.spec.components[name="prefill"].template.spec.containers` as one leaf, the embedded
  schema records `.spec.components[name="prefill"].template.spec.containers[name="app"].image`
  etc. Control `TestFieldSetParityControlKind` (ClusterEngineRuntimeProfile, no schemaless
  subtrees): **PASS**.
- `TestExtractRoleInstanceKeepsServerManagedTemplate`: **FAIL** — after applying a
  RoleInstance through the server-side converter (managedfieldstest) and attaching the
  recorded managedFields, the generated `applyv1alpha2.ExtractRoleInstance` returns each
  component with `template.spec` empty: pod template containers are dropped. An
  extract→modify→apply cycle against a real cluster would therefore delete them.
  Control `TestExtractWithServerSchemaKeepsTemplate` (same managed fields, CRD-derived
  parseable type): **PASS** — containers survive, so the harness and the fix direction are
  sound.
- `TestExtractModifyApplyDropsServerManagedTemplate`: **FAIL** — the full round trip
  (server apply -> generated `ExtractRoleInstance` -> bump an owned scalar -> re-apply as
  the same manager) leaves the live object with `template.spec.containers` **absent** for
  both components: SSA prunes the owned fields the mangled extraction omitted. This is the
  on-cluster data loss, reproduced with kube-apiserver's own field-manager semantics.
- `TestFakeMatchesServerInstanceComponents`: **FAIL** — the server rejects a second
  manager's apply of a different v1alpha1 components list with
  `conflict with "manager-a": .spec.components`; `fake.NewClientset()` silently merges
  (components become `[prefill decode]`). Control
  `TestFakeMatchesServerRoleInstanceComponents` (v1alpha2 list-map on both sides):
  **PASS**.

## Proposed fixes (NOT applied to production here)

- **F1**: derive the embedded schema from `config/crd/bases` with the apiextensions-apiserver
  OpenAPI v3 builder (exactly what the PR body describes for its second revision), so the
  fake and `Extract<Kind>` follow the CRDs; keep this harness's parity test as the guard.
  Alternatively, change the CRDs to fully structural schemas — a much bigger API change.
